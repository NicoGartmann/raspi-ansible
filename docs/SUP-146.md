# SUP-146: Migrations-Schritte & `raspi-ansible` Anpassungen

Dieses Dokument ergänzt das Design-Dokument [`docs/SUP-146.md`](https://github.com/NicoGartmann/docker-config/blob/main/docs/SUP-146.md) im `docker-config`-Repository und beschreibt alle notwendigen Schritte im `raspi-ansible`-Projekt sowie die Datenmigration auf den Zielgeräten (`raspberrypi`, `parents_pi` und `strato_vps`).

---

## 1. Konzept: Host-spezifische Vaults (`vaults/<hostname>.yml`)

Da jeder Twingate-Connector (`raspberrypi`, `parents_pi`, `strato_vps`) eigene Zugangs-Tokens (`TWINGATE_ACCESS_TOKEN`, `TWINGATE_REFRESH_TOKEN`) erhält und auch `SAMBA_PASSWORD` pro Pi getrennt verwaltet wird, nutzt `raspi-ansible` **getrennte Vault-Dateien pro Host**:

```text
vaults/
├── raspberrypi.yml      # Connector-Tokens & Samba-Passwort für raspberrypi
├── parents_pi.yml       # Connector-Tokens & Samba-Passwort für parents_pi (neu anlegen)
└── strato_vps.yml       # Connector-Tokens für strato_vps
```

* **Automatisches Laden pro Host**: Die Rolle [`roles/docker_compose/tasks/main.yml`](../roles/docker_compose/tasks/main.yml) lädt über `vaults/{{ inventory_hostname }}.yml` automatisch immer genau den Vault, der zum aktuell ausgerollten Host gehört.
* **Aufbau jeder `vaults/<hostname>.yml`**:
  ```yaml
  ---
  vault_twingate_network: "<dein-twingate-netzwerk>"
  vault_twingate_access: "<connector-access-token-des-jeweiligen-hosts>"
  vault_twingate_refresh: "<connector-refresh-token-des-jeweiligen-hosts>"
  vault_samba_password: "<samba-passwort-des-jeweiligen-hosts>" # nur auf raspberrypi & parents_pi benötigt
  ```

## 2. Anpassungen im `raspi-ansible`-Repository

### 2.1 Atomares `.env`-Schreiben und `--env-file` in `roles/docker_compose/tasks/main.yml` & `playbooks/update.yml`
1. **Atomares Schreiben von `/opt/services/.env`**:
   Da `.env` im `docker-config`-Repository nicht mehr in Git getrackt wird, verwaltet Ansible die Datei `/opt/services/.env` vollständig über `ansible.builtin.copy` (statt einzelner `lineinfile`-Aufrufe). Dadurch werden alle Einträge aus `compose_env_vars` in einem einzigen Task geschrieben und veraltete Variablen (wie `RCLONE_CONFIG`) automatisch bereinigt.
2. **Explizites `--env-file` für Themen-Unterordner**:
   Da die Compose-Dateien in Themen-Unterordnern (`connectivity/adguard.yml`, `documents/docker-compose.yml` usw.) liegen, sucht Docker Compose die `.env`-Datei standardmäßig im jeweiligen Unterordner statt unter `/opt/services/.env`. In [`roles/docker_compose/tasks/main.yml`](../roles/docker_compose/tasks/main.yml) und [`playbooks/update.yml`](../playbooks/update.yml) wird der Aufruf daher um `--env-file` ergänzt:

```yaml
# Pull:
cmd: "docker compose --env-file {{ compose_repo_dest | default('/opt/services') }}/.env -f {{ item }} pull"

# Up:
cmd: "docker compose --env-file {{ compose_repo_dest | default('/opt/services') }}/.env -f {{ item }} up -d"
```

### 2.2 Aktualisierung von [`inventory/host_vars/raspberrypi/vars.yml`](../inventory/host_vars/raspberrypi/vars.yml)
* Umstellung von `compose_files` auf die neuen Themen-Dateien.
* Da für alle Standardpfade auf `raspberrypi` bereits `${VAR:-default}`-Fallbacks in `docker-config` hinterlegt sind, enthält `compose_env_vars` nur noch die echten Vault-Geheimnisse und `compose_directories` nur noch Verzeichnisse, die `1000:1000` (statt `root:root`) gehören müssen:

```yaml
compose_files:
  - "connectivity/adguard.yml"
  - "connectivity/proxy.yml"
  - "connectivity/twingate.yml"
  - "documents/docker-compose.yml"
  - "storage/samba.yml"
  - "monitoring/agent.yml"

compose_directories:
  - { path: /mnt/drive/paperless, owner: "1000", group: "1000", mode: "0755" }
  - { path: /mnt/drive/nas, owner: "1000", group: "1000", mode: "0755" }

compose_env_vars:
  - { key: "TWINGATE_NETWORK", value: "{{ vault_twingate_network }}" }
  - { key: "TWINGATE_ACCESS_TOKEN", value: "{{ vault_twingate_access }}" }
  - { key: "TWINGATE_REFRESH_TOKEN", value: "{{ vault_twingate_refresh }}" }
  - { key: "SAMBA_PASSWORD", value: "{{ vault_samba_password }}" }
```

### 2.3 Aktualisierung von [`inventory/host_vars/parents_pi/vars.yml`](../inventory/host_vars/parents_pi/vars.yml)
* Aktivierung von `compose_repo_url`, `compose_files` (inkl. `proxy.yml` und `twingate.yml`), `compose_directories` und `compose_env_vars`.
* Alle Standard- und Medien-Pfade (`/opt/plex`, `/opt/overseerr`, `/mnt/mediahdd/Serien`, `/mnt/mediahdd/Filme`, `/mnt/oldhdd/Bilder`) greifen über die `${VAR:-default}`-Fallbacks in `docker-config`. In `compose_env_vars` werden daher nur der vom Default abweichende Samba-Pfad (`SAMBA_DATA=/mnt`) sowie die Geheimnisse aus `vaults/parents_pi.yml` gesetzt:

```yaml
compose_repo_url: "https://github.com/NicoGartmann/docker-config.git"
compose_repo_dest: "/opt/services"
compose_repo_version: "main"

compose_files:
  - "connectivity/adguard.yml"
  - "connectivity/proxy.yml"
  - "connectivity/twingate.yml"
  - "media/docker-compose.yml"
  - "storage/samba.yml"
  - "monitoring/agent.yml"

compose_directories:
  - { path: /opt/plex, owner: "1000", group: "1000", mode: "0755" }
  - { path: /opt/overseerr, owner: "1000", group: "1000", mode: "0755" }

compose_env_vars:
  - { key: "SAMBA_DATA", value: "/mnt" }
  - { key: "TWINGATE_NETWORK", value: "{{ vault_twingate_network }}" }
  - { key: "TWINGATE_ACCESS_TOKEN", value: "{{ vault_twingate_access }}" }
  - { key: "TWINGATE_REFRESH_TOKEN", value: "{{ vault_twingate_refresh }}" }
  - { key: "SAMBA_PASSWORD", value: "{{ vault_samba_password }}" }
```

### 2.4 Vorbereitung von [`inventory/host_vars/strato_vps/vars.yml`](../inventory/host_vars/strato_vps/vars.yml)
Auch auf `strato_vps` wird `connectivity/twingate.yml` ausgerollt, sobald die beiden Pis migriert und die Connector-Tokens in `vaults/strato_vps.yml` hinterlegt sind:

```yaml
compose_repo_url: "https://github.com/NicoGartmann/docker-config.git"
compose_repo_dest: "/opt/services"
compose_repo_version: "main"

compose_files:
  - "connectivity/twingate.yml"

compose_env_vars:
  - { key: "TWINGATE_NETWORK", value: "{{ vault_twingate_network }}" }
  - { key: "TWINGATE_ACCESS_TOKEN", value: "{{ vault_twingate_access }}" }
  - { key: "TWINGATE_REFRESH_TOKEN", value: "{{ vault_twingate_refresh }}" }
```

## 3. Migrations-Checkliste für die Zielgeräte

> [!IMPORTANT]
> **Reihenfolge beim Erst-Rollout: Zwingend `playbooks/docker-compose.yml` vor `playbooks/update.yml` ausführen!**
> Da `.env` in `docker-config` per `git rm --cached .env` aus dem Git-Tracking entfernt wurde, löscht `git` beim ersten Pull auf den neuen `main`-Stand die bisherige `/opt/services/.env`.
> `playbooks/update.yml` setzt eine existierende `/opt/services/.env` voraus, legt sie aber (um im Alltag ohne `--ask-vault-pass` zu laufen) nicht selbst an. Daher muss bei der Migration auf jedem Host zuerst **`playbooks/docker-compose.yml --ask-vault-pass`** ausgeführt werden.

### 3.1 Migration auf `raspberrypi`

> [!CAUTION]
> **Schutz der Paperless-Bestandsdaten (`/mnt/drive/paperless`)**
> Auf `raspberrypi` liegen alle produktiven Daten von Paperless-ngx (`pgdata`, `data`, `media`, `consume`, `export`) direkt auf der externen Festplatte unter `/mnt/drive/paperless`, sowie die App-Configs unter `/opt/adguard` und `/opt/nginx-proxy-manager`.
> Da alle Pfade als Host-Bind-Mounts eingebunden sind und sich in den neuen Compose-Dateien **nicht ändern**, bleiben beim Neustart über die neuen Themen-Stacks sämtliche Datenbank-Einträge und Dokumente 1:1 erhalten.

1. **Alten monolithischen Compose-Stack auf `raspberrypi` stoppen und obsoletes `/opt/rclone`-Verzeichnis entfernen**:
   *(Hinweis: Da `docker compose down` auch den alten `twingate-connector` stoppt, diesen Schritt im lokalen Heimnetz ausführen.)*
   ```bash
   ssh nico@192.168.178.10 "cd /opt/services && sudo docker compose down && sudo rm -rf /opt/rclone"
   ```
2. **Neue Themen-Stacks samt neuer `/opt/services/.env` über Ansible ausrollen**:
   ```bash
   ansible-playbook playbooks/docker-compose.yml --limit raspberrypi --ask-vault-pass
   ```

---

### 3.2 Migration auf `parents_pi` (Remote über Twingate)

> [!CAUTION]
> **Schutz der Plex-Medien & Metadaten + Remote-Zugriff über `twingate-large-junglefowl`**
> * Die Medien-Verzeichnisse (`/mnt/mediahdd/Serien`, `/mnt/mediahdd/Filme`, `/mnt/oldhdd/Bilder`) bleiben unangetastet.
> * Da die Migration aus der Ferne über Twingate erfolgt, **darf der aktuell laufende Container `twingate-large-junglefowl` erst gestoppt werden, nachdem der neue Stack läuft**. Da `twingate-large-junglefowl` nicht Teil von `/home/pi/docker-conf/docker-compose.yml` ist, bleibt die Twingate-Verbindung beim Stoppen von `/home/pi/docker-conf` vollständig bestehen.

1. **Host-spezifischen Vault `vaults/parents_pi.yml` anlegen**:
   ```bash
   ansible-vault create vaults/parents_pi.yml
   ```
   > [!TIP]
   > **Unterbrechungsfreier Twingate-Wechsel aus der Ferne (`twingate-large-junglefowl` → `twingate-connector`)**:
   > * **Variante A (Empfohlen – neuer Connector im Twingate Admin Panel)**: Erstelle im Twingate Admin Panel für das Eltern-Netzwerk einen neuen Connector und trage dessen frische Tokens in `vaults/parents_pi.yml` ein. Dadurch startet Ansible in Schritt 4 den neuen Container `twingate-connector` parallel zu `twingate-large-junglefowl`, ohne dass sich beide um dasselbe Token streiten. Sobald der neue Connector im Twingate Admin Panel auf *Connected* steht, kannst du `twingate-large-junglefowl` in Schritt 5 gefahrlos löschen.
   > * **Variante B (Gleiche Tokens wiederverwenden)**: Wenn du exakt dieselben Tokens wie `twingate-large-junglefowl` in `vaults/parents_pi.yml` einträgst, stoppe direkt nach Schritt 4 den alten Container und starte den neuen in einem einzigen verketteten Befehl neu:
   >   `ssh nico@192.168.178.46 "sudo docker rm -f twingate-large-junglefowl && sudo docker compose --env-file /opt/services/.env -f /opt/services/connectivity/twingate.yml restart"`

2. **Alten Compose-Stack unter `/home/pi/docker-conf` stoppen (zwingend VOR dem Verschieben der Verzeichnisse!)**:
   > [!WARNING]
   > Die Container aus `/home/pi/docker-conf` (`plex`, `overseerr`, `adguard`, `samba`) **müssen zwingend gestoppt sein**, bevor in Schritt 3 die Konfigurationsordner verschoben werden. Andernfalls entzieht man den laufenden Prozessen zur Laufzeit ihre offenen SQLite-Datenbanken und Konfigurationsdateien, was zu Datenkorruption führen kann. (`twingate-large-junglefowl` läuft separat weiter, sodass deine SSH-Verbindung bestehen bleibt.)
   ```bash
   ssh nico@192.168.178.46 "cd /home/pi/docker-conf && sudo docker compose down && sudo docker ps"
   ```
   *(In der Ausgabe von `sudo docker ps` sollte jetzt nur noch `twingate-large-junglefowl` zu sehen sein.)*

3. **Bestandsdaten aus `/home/pi/docker-conf` atomar nach `/opt` verschieben**:
   *(Hinweis: `/opt/plex` und `/opt/overseerr` werden vorher bewusst **nicht** per `mkdir` angelegt, damit `sudo mv` das jeweilige `config`-Verzeichnis inkl. versteckter Dotfiles als Ganzes atomar nach `/opt/plex` bzw. `/opt/overseerr` umbenennt.)*
   ```bash
   ssh nico@192.168.178.46 "
     sudo mkdir -p /opt/adguard &&
     sudo mv /home/pi/docker-conf/adguard/data /opt/adguard/work &&
     sudo mv /home/pi/docker-conf/adguard/config /opt/adguard/conf &&
     sudo mv /home/pi/docker-conf/plex/config /opt/plex &&
     sudo mv /home/pi/docker-conf/overseerr/config /opt/overseerr &&
     sudo chown -R 1000:1000 /opt/plex /opt/overseerr
   "
   ```
   > [!NOTE]
   > * Beachte bei AdGuard die Umbenennung der Unterordner von `data` → `work` und `config` → `conf`, damit die Ordnerstruktur unter `/opt/adguard` auf beiden Pis identisch ist.
   > * Prüfe vor Schritt 4 in `/opt/adguard/conf/AdGuardHome.yaml` zwei Einstellungen für den Wechsel vom bisherigen `network_mode: host` auf Bridge:
   >   1. Unter `http: address:` muss `0.0.0.0:80` stehen (für das Port-Mapping `8080:80`).
   >   2. Unter `dns: bind_hosts:` muss `0.0.0.0` (und **nicht** die feste Host-LAN-IP `192.168.178.46`) eingetragen sein, da das Bridge-Interface im Container die Host-IP nicht besitzt.

4. **Neue Themen-Stacks über Ansible ausrollen**:
   ```bash
   ansible-playbook playbooks/docker-compose.yml --limit parents_pi --ask-vault-pass
   ```

5. **Alten Twingate-Container entfernen & Aufräumen nach erfolgreichem Funktionstest**:
   * Sobald der neue `twingate-connector` läuft und verbunden ist, den alten Container entfernen:
     ```bash
     ssh nico@192.168.178.46 "sudo docker rm -f twingate-large-junglefowl"
     ```
   * Nach erfolgreichem Test aller Dienste (Plex, Overseerr, AdGuard, NPM, Twingate, Samba) kann `/home/pi/docker-conf` auf `parents_pi` gelöscht (`sudo rm -rf /home/pi/docker-conf`) und das GitHub-Repository `docker-conf` archiviert werden.
